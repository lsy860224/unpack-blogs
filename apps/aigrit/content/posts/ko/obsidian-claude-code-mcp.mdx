**TL;DR: Obsidian vault를 Claude Code의 컨텍스트로 물리고, Claude가 만든 코드·로그를 다시 같은 vault로 떨어뜨리면, 노트와 코드가 한 워크플로우로 합쳐진다. 1인 빌더에게는 사실상 GUI 없는 IDE다.**

작성자는 블로그와 앱을 만들며 작업 기록과 코드 베이스를 자주 오간다. Obsidian에서 기획을 적고, 터미널에서 [Claude Code](https://github.com/anthropics/claude-code)로 구현하고, 다시 Obsidian으로 돌아와 결과를 정리하는 흐름이다. 그 사이를 [Model Context Protocol](https://modelcontextprotocol.io)과 Claude Code의 파일 접근이 연결하면서 복사·붙여넣기 왕복이 크게 줄었다. 이 글은 그 연결 구조와 설정, 실전 사용 패턴을 정리한 기록이다. MCP 자체의 개요와 다른 도구 연동은 <Link href="/ko/blog/claude-mcp-guide">Claude MCP 활용법</Link>에 따로 정리해 두었으니, 본 글은 "Obsidian + Claude Code" 한 조합에 집중한다.

## 왜 이 조합인가 — 노트와 코드의 분리 비용

1인 빌더가 가장 자주 잃는 것은 "맥락"이다. 어제 적은 기획 노트, 오늘 짠 코드, 내일 정리할 회고가 서로 다른 앱에 흩어져 있으면 같은 결정을 두 번씩 내리게 된다. 기존에는 Obsidian에서 기획을 짜고, VS Code나 [Cursor](https://cursor.com)에 옮겨 코드를 작성하고, 결과를 다시 Obsidian으로 복사해 정리하는 식이었다. 한 번의 기능 추가에 같은 텍스트가 세 번 이동했다.

Claude Code는 터미널에서 직접 파일을 읽고 쓴다. 여기에 Obsidian MCP 서버를 더하면, Claude는 vault의 노트를 코드 베이스의 일부처럼 다룰 수 있다. <Link href="/ko/blog/obsidian-getting-started">Obsidian 시작하기</Link>에서 적었듯, vault는 결국 마크다운 파일 폴더다. Claude Code 입장에서는 다른 git 레포 하나가 더 붙은 것과 비슷하다. 두 도구의 비교가 필요하다면 <Link href="/ko/blog/claude-code-vs-cursor">Claude Code vs Cursor</Link>를 같이 보자.

이 조합의 핵심 효과는 단순하다. **기획·구현·회고가 한 명령어 안에서 끝난다.** "이 노트 읽고, 그대로 implementation 만들고, 끝나면 변경사항을 같은 노트 하단에 요약해" 한 줄이면 된다. 구조로 보면 Obsidian vault와 Claude Code 터미널 사이에 MCP 서버 하나가 다리 역할로 들어가는 형태다. 양쪽이 서로의 파일을 직접 만지지는 않지만, MCP가 같은 컨텍스트 위에서 둘을 동시에 다루도록 묶어준다.

## 연결 구조 — MCP 서버가 양쪽을 잇는 방식

MCP는 Anthropic이 공개한 오픈 프로토콜이다. 클라이언트(Claude Desktop·Claude Code)와 서버(도구 어댑터) 사이의 표준 통신 규약이다. 로컬 Obsidian MCP 서버는 보통 stdio 방식으로 실행되어 vault 폴더를 도구로 노출한다. Claude Code는 그 서버를 호출해 노트를 읽고, 새 노트를 생성하고, frontmatter를 수정한다.

| 레이어 | 역할 | 실제 구성 |
|---|---|---|
| 클라이언트 | 명령 입력 + LLM 추론 | Claude Code CLI (터미널) |
| 프로토콜 | JSON-RPC 표준 | MCP (로컬 stdio · 원격 Streamable HTTP) |
| 서버 | 도구 어댑터 | obsidian-mcp · filesystem MCP |
| 데이터 | 마크다운 노트 + 코드 파일 | Obsidian vault + git 레포 |

Claude Code 자체가 이미 로컬 파일시스템에 접근한다. 그래서 vault를 Claude Code의 작업 디렉토리 안에 두면 별도 MCP 서버 없이도 노트를 읽을 수 있다. 다만 검색·태그·백링크 같은 Obsidian 고유 기능을 활용하려면 전용 MCP 서버가 더 강력하다. 이 글에서는 둘 다 다룬다.

## 설정 단계 — Claude Code CLI + Obsidian MCP 등록

먼저 [Claude Code](https://code.claude.com/docs/en/overview)를 설치한다. 공식 문서는 네이티브 설치를 권장한다.

```bash
# macOS · Linux
curl -fsSL https://claude.ai/install.sh | bash
claude --version
```

npm(`npm install -g @anthropic-ai/claude-code`)으로도 설치할 수 있다. Claude Code를 쓰려면 Claude 유료 플랜(Pro 이상) 또는 API 키가 필요하다.

다음으로 MCP 서버를 등록한다. 가장 간단한 방법은 `claude mcp add` 명령이다. `--` 뒤에 서버 실행 명령을 그대로 적는다.

```bash
# 커뮤니티 서버 obsidian-mcp — vault 경로를 인자로 전달
claude mcp add --transport stdio obsidian -- npx -y obsidian-mcp /Users/me/Obsidian/main-vault

# MCP 공식 참조 Filesystem 서버
claude mcp add --transport stdio filesystem -- npx -y @modelcontextprotocol/server-filesystem /Users/me/Obsidian/main-vault
```

`--scope`(`-s`)로 범위를 정한다. 기본값 local은 현재 프로젝트에서 나만 쓰고 `~/.claude.json`에 저장되며, `-s project`는 프로젝트 루트의 `.mcp.json`에 저장돼 팀과 공유된다. `.mcp.json`에 직접 적으면 이런 모양이다.

```json
{
  "mcpServers": {
    "obsidian": {
      "command": "npx",
      "args": ["-y", "obsidian-mcp", "/Users/me/Obsidian/main-vault"]
    },
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/me/Obsidian/main-vault"]
    }
  }
}
```

등록 후 Claude Code 안에서 `/mcp`를 입력하면 서버별 연결 상태가 보이고, 셸에서는 `claude mcp list`로 확인할 수 있다. `obsidian-mcp`는 노트 읽기·생성·수정, vault 검색, 태그 관리 도구를 제공하는 커뮤니티 서버이고, Filesystem 서버는 일반 파일 작업용이다. 둘 중 하나만 써도 되며, 같은 vault를 두 서버로 동시에 수정하면 추적이 어려우니 역할을 나눠 두자. 프로젝트 범위 서버는 처음 사용할 때 승인을 요청한다.

여기까지가 기본 골격이다. 자동화 스택의 다른 도구와 조합하는 방법은 <Link href="/ko/blog/solo-developer-automation-stack">1인 개발자 자동화 스택</Link>을 참고하자.

## 실전 사용 패턴 1 — 노트에서 코드로

가장 자주 쓰는 흐름이다. Obsidian에 적어둔 기획 노트를 Claude Code가 읽어 코드로 바꾸는 방향이다. 예를 들어 `Projects/seo-dashboard/spec.md`에 입력 스키마와 화면 구조를 정리해 두었다고 하자. 터미널에서는 한 줄이면 된다.

```bash
claude "Projects/seo-dashboard/spec.md 를 읽고 Next.js 16 App Router로 구현해. content/dashboard 디렉토리에 RSC로 짜고, 검증은 zod로."
```

Claude Code는 노트를 그대로 컨텍스트에 올린 뒤, 프로젝트 컨벤션을 추적하면서 파일을 생성한다. 기획서가 길어질수록 효과가 크다. 1,500자짜리 spec을 매번 채팅창에 붙여 넣는 부담이 사라지기 때문이다. 비슷한 패턴을 Flutter 앱에 적용한 사례는 <Link href="/ko/blog/claude-code-flutter-app-guide">Claude Code Flutter 앱 가이드</Link>에 정리했다.

이때 중요한 한 가지. **Claude Code의 컨텍스트는 무한이 아니다.** vault 전체를 통째로 읽히려 하면 토큰이 폭발한다. 노트를 호출할 때는 정확한 경로를 지정하거나, MCP 서버의 검색 도구로 필요한 노트만 찾게 하는 편이 안전하다. 명령이 끝나면 vault의 `spec.md`는 그대로 남고, 코드 트리에 `app/dashboard/page.tsx` 같은 새 파일이 생기면서 두 폴더가 한 번에 갱신된다.

## 실전 사용 패턴 2 — 코드에서 노트로

반대 방향도 자주 쓴다. 커밋 직후 Claude Code에 "오늘 변경 요약을 `99. Devlog/2026-05-04.md`에 추가해" 같은 요청을 넣는다. Claude는 `git diff`와 최근 커밋 메시지를 읽고, vault의 데일리 노트에 변경 요약을 append한다. 코드 변경의 "왜"를 매일 자동으로 vault에 누적하는 흐름이다.

```bash
claude "오늘 main 에 들어간 변경사항을 요약해서 Obsidian 의 99. Devlog/$(date +%Y-%m-%d).md 끝에 ## 변경 요약 섹션으로 추가해"
```

이렇게 쌓인 데일리 로그는 회고에 그대로 쓰인다. 같은 작업을 [Make](https://www.make.com) 같은 자동화 도구로도 할 수 있지만, diff를 읽고 자연어로 요약하는 부분은 LLM이 맡기 좋은 일이다. 비교는 <Link href="/ko/blog/make-automation-guide">Make 자동화 가이드</Link>에 정리해 두었다.

## 실전 사용 패턴 3 — 양방향 동기화

세 번째 패턴은 docstring과 노트를 한 쌍으로 묶는 방법이다. 함수 docstring을 vault 노트에 임베드 형식으로 옮겨두면, 코드를 수정할 때마다 Claude가 docstring과 노트를 동시에 갱신한다.

```bash
claude "src/lib/seo.ts 의 함수별 docstring 을 읽고, Obsidian 의 70. Reference/seo-functions.md 에 동일한 시그니처로 동기화해. 신규 함수는 추가, 사라진 함수는 archive 표기."
```

반복해서 쓰는 명령은 셸 별칭이나 단축키로 묶어 두면 편하다. 모바일·Mac 단축키로 AI 작업을 묶는 방법은 <Link href="/ko/blog/apple-shortcuts-ai-automation">Apple 단축어 AI 자동화</Link>에 정리했다. 다만 자동 갱신 결과는 커밋 전에 diff로 확인하는 습관을 두자.

## 작성자의 실제 사례 — Obsidian SEO 대시보드

이 글에서 설명한 구조는 [babipanote의 Obsidian SEO 대시보드](https://babipanote.com/blog/obsidian-seo-dashboard)에서 실제로 돌아간다. GSC에서 받은 키워드 데이터를 vault 노트에 누적하고, Claude Code가 그 노트를 읽어 다음 글의 키워드 우선순위를 정하는 흐름이다. 데이터 쪽은 Python 스크립트가 채우고, "다음에 뭐 쓸까" 판단은 Claude Code가 내린다. 노트와 코드가 한 vault에 같이 있으니, 키워드 한 줄을 보고 그대로 새 MDX 초안 파일까지 같은 명령에서 생성된다.

구조를 다시 정리하면 Obsidian이 데이터 레이어, Claude Code가 작업 레이어, MCP가 통신 레이어다.

## 트러블슈팅 — 자주 만나는 문제 3가지

**1. `Server failed to start: ENOENT npx`**
서버 실행 명령(`npx`)을 찾지 못하는 경우다. nvm 같은 버전 관리자로 Node.js를 설치했다면 셸 설정에 따라 경로가 잡히지 않을 수 있다. `which npx`로 절대 경로를 확인해 `command`에 직접 적으면 해결된다.

**2. vault 경로 문제**
vault 경로는 절대 경로로 적어야 한다. 공백이 들어간 경로는 `claude mcp add` 명령에서 따옴표로 감싸고, 서버가 경로를 제대로 인식하는지 `/mcp`에서 확인하자.

**3. 허용 폴더 밖 접근 거부**
Filesystem 서버는 인자로 넘긴 폴더 밖의 파일 접근을 막는다. 의도된 동작이다. 다른 폴더도 다뤄야 한다면 인자에 그 폴더를 추가로 적는다.

## 자주 묻는 질문 (FAQ)

### Claude Desktop과 Claude Code 중 어느 쪽이 Obsidian MCP에 더 적합한가요?

작업 성격에 따라 갈립니다. 노트만 다루는 흐름은 Claude Desktop으로 충분하고, 노트와 코드를 함께 편집하고 git까지 다룬다면 Claude Code가 편합니다. 같은 MCP 서버를 두 앱에 각각 등록할 수 있어, 작업에 따라 골라 쓰면 됩니다.

### Obsidian MCP 서버는 vault 전체를 읽나요? 보안이 걱정됩니다.

서버 인자로 넘긴 vault 폴더 안에서 읽기·쓰기가 가능하므로, 민감한 노트는 별도 vault로 분리하는 편이 안전합니다. 로컬 서버 자체는 내 컴퓨터에서 실행되지만, Claude가 읽은 노트 내용은 대화의 일부로 Anthropic에 전달된다는 점을 기억하세요.

### vault가 크면 어떻게 쓰는 게 좋나요?

노트가 많을수록 전체를 읽히는 요청은 느리고 컨텍스트를 많이 씁니다. 작업할 폴더나 파일 경로를 구체적으로 지정하고, 검색 도구로 필요한 노트만 찾게 하세요. 자주 쓰는 노트 위치는 프로젝트의 CLAUDE.md에 적어 두면 매번 설명하지 않아도 됩니다.

### 이 조합은 윈도우에서도 잘 돌아가나요?

됩니다. Claude Code는 Windows용 설치 스크립트(PowerShell)를 제공합니다. 다만 경로 구분자와 셸 차이 때문에 npx 기반 서버는 `cmd /c npx ...` 형태로 감싸야 하는 경우가 있습니다. 설정 방법은 Claude Code 공식 MCP 문서의 Windows 안내를 확인하세요.

### 무료로 쓸 수 있나요?

Obsidian 앱과 MCP 서버들은 무료입니다. 하지만 Claude Code는 Claude 무료 플랜에 포함되지 않아, Pro(월 20달러) 이상 유료 플랜이나 API 키(사용량 과금)가 필요합니다. 사용량이 많아 한도에 자주 걸리면 Max 플랜이나 API 과금 방식을 비교해 보세요.

Obsidian과 Claude Code는 따로 쓰면 좋은 도구지만, MCP로 묶어 두면 1인 빌더에게는 한 단계 다른 환경이 된다. 노트가 곧 컨텍스트가 되고, 코드 변경이 곧 회고로 쌓인다. GUI에 의존하지 않는 워크플로우가 가능해진다는 뜻이다. 같은 흐름 안에서 기획·구현·기록을 이어 갈 수 있다는 점이 가장 큰 장점이다.
