## 한 줄 요약

**Claude Agent SDK** 로 첫 자율 에이전트를 만드는 일은 생각보다 짧다. 패키지 설치 → 커스텀 **툴 정의** → `query` 로 에이전트 **루프** 실행, 이 세 단계면 툴 하나짜리 에이전트가 돈다. 이 글은 TypeScript와 Python 코드를 나란히 놓고, 빈 폴더에서 동작하는 에이전트까지 단계별로 진행한 뒤 배포까지의 흐름을 정리한다.

<Callout type="info" title="실습 환경">
  대상: Node.js 18+ 또는 Python 3.10+ · 패키지: `@anthropic-ai/claude-agent-sdk`(TS) / `claude-agent-sdk`(Python) · 사전 준비: Anthropic API 키 1개 · 예제: 좌표를 받아 날씨를 돌려주는 커스텀 툴 1개를 정의해 에이전트가 스스로 호출하게 만든다. 코드는 2026년 SDK 기준이며, API는 변경될 수 있으니 공식 문서를 함께 확인하시기 바랍니다.
</Callout>

이 글은 에이전트가 *무엇인지*는 이미 안다고 가정한다. 정의·구조·도구 비교가 궁금하다면 먼저 <Link href="/ko/blog/ai-agent-complete-guide-2026">AI 에이전트 완벽 가이드 2026</Link>을 읽고 오는 편이 좋다. 여기서는 그 가이드의 4요소 중 *툴 호출과 루프*를 코드로 직접 구현한다.

## 왜 Claude Agent SDK인가

같은 에이전트를 만드는 길은 여럿이지만, **Claude Agent SDK** 는 Claude를 중심에 둘 때 보일러플레이트가 가장 적다. 툴 정의·MCP·서브에이전트가 네이티브로 묶여 있어, 다른 프레임워크에서 수십 줄이 필요한 일을 함수 하나로 끝낸다.

![Claude Agent SDK·LangChain·OpenAI SDK 입문 비교 — 설치·툴 정의·루프 구현·MCP 지원](/images/claude-agent-sdk-getting-started/01-overview.png)

| 항목 | Claude Agent SDK | LangChain | 직접 API 호출 |
|------|:----------------:|:---------:|:------------:|
| **언어** | TS · Python | Python · JS | 모든 언어 |
| **툴 정의** | `tool()` 한 줄 | 클래스·데코레이터 | 수동 스키마 |
| **에이전트 루프** | `query` 내장 | AgentExecutor | 직접 구현 |
| **MCP 지원** | 네이티브 | 어댑터 | 없음 |
| **보일러플레이트** | 적음 | 많음 | 매우 많음 |

직접 API를 호출하면 툴 스키마·루프·재시도를 전부 손으로 짜야 한다. LangChain은 범용적이지만 추상화가 두껍다. 입문 단계에서 *가장 적은 코드로 도는 에이전트*를 보려면 Claude Agent SDK가 빠르다. 코딩 에이전트 도구 자체를 비교한 글은 <Link href="/ko/blog/claude-code-vs-cursor">Claude Code vs Cursor 비교</Link>에 있다.

## Step 1 — 설치와 API 키

먼저 SDK를 설치하고 API 키를 환경변수로 등록한다. [Claude Agent SDK](https://docs.claude.com/en/api/agent-sdk/overview)는 TypeScript와 Python을 모두 지원한다.

```bash
# TypeScript
npm install @anthropic-ai/claude-agent-sdk

# Python
pip install claude-agent-sdk

# API 키 등록 (공통)
export ANTHROPIC_API_KEY=sk-ant-...
```

API 키는 [Anthropic Console](https://console.anthropic.com)에서 발급한다. 키를 코드에 직접 박지 말고 반드시 환경변수로 두는 것이 보안 기본이다.

## Step 2 — 커스텀 툴 정의하기

에이전트가 외부 세계와 만나는 통로가 **툴**이다. 좌표를 받아 현재 기온을 돌려주는 `get_weather` 툴을 정의하고, 이를 in-process MCP 서버로 묶는다. TypeScript는 [Zod](https://zod.dev)로 입력 스키마를 검증한다.

```typescript
import { query, tool, createSdkMcpServer } from "@anthropic-ai/claude-agent-sdk";
import { z } from "zod";

// 커스텀 툴 1개를 in-process MCP 서버로 묶는다
const weatherServer = createSdkMcpServer({
  name: "weather-tools",
  version: "1.0.0",
  tools: [
    tool(
      "get_weather",
      "좌표로 현재 기온을 조회한다",
      {
        latitude: z.number().describe("위도"),
        longitude: z.number().describe("경도"),
      },
      async (args) => {
        const res = await fetch(
          `https://api.open-meteo.com/v1/forecast?latitude=${args.latitude}&longitude=${args.longitude}&current=temperature_2m`
        );
        const data = await res.json();
        return {
          content: [
            { type: "text", text: `현재 기온: ${data.current.temperature_2m}°C` },
          ],
        };
      }
    ),
  ],
});
```

Python도 구조가 같다. `@tool` 데코레이터로 함수에 이름·설명·입력 스키마를 붙이고, `create_sdk_mcp_server` 로 묶는다.

```python
from claude_agent_sdk import tool, create_sdk_mcp_server
import aiohttp

@tool("get_weather", "좌표로 현재 기온을 조회한다", {"latitude": float, "longitude": float})
async def get_weather(args):
    url = (
        "https://api.open-meteo.com/v1/forecast"
        f"?latitude={args['latitude']}&longitude={args['longitude']}&current=temperature_2m"
    )
    async with aiohttp.ClientSession() as session:
        async with session.get(url) as res:
            data = await res.json()
    return {"content": [{"type": "text", "text": f"현재 기온: {data['current']['temperature_2m']}°C"}]}

weather_server = create_sdk_mcp_server(
    name="weather-tools", version="1.0.0", tools=[get_weather]
)
```

툴이 돌려주는 값은 반드시 `content` 키를 가진 딕셔너리여야 한다. 이 형식이 곧 모델이 읽는 *관찰 결과*가 된다. 툴을 MCP로 노출하는 개념을 더 깊이 보려면 <Link href="/ko/blog/claude-mcp-guide">Claude MCP 완벽 가이드</Link>를 참고하면 된다.

## Step 3 — 에이전트 루프 실행하기

이제 정의한 툴을 에이전트에게 넘기고 목표를 던진다. `query` 가 *계획 → 툴 호출 → 관찰 → 판단*의 루프를 내부에서 자동으로 돈다. `allowedTools` 로 어떤 툴을 권한 승인 없이 쓰게 할지 지정한다.

```typescript
async function* userMessage() {
  yield {
    type: "user" as const,
    message: { role: "user" as const, content: "서울 날씨 알려줘" },
  };
}

for await (const message of query({
  prompt: userMessage(),
  options: {
    mcpServers: { "weather-tools": weatherServer },
    allowedTools: ["mcp__weather-tools__get_weather"],
    maxTurns: 3, // 루프 폭주를 막는 안전장치
  },
})) {
  if (message.type === "result" && message.subtype === "success") {
    console.log(message.result);
  }
}
```

여기서 일어나는 일이 바로 에이전트 루프다. 모델은 "서울 날씨"를 받아 *스스로* 서울의 좌표를 추론하고, `get_weather` 툴을 호출하고, 돌아온 기온을 읽어 자연어 답을 만든다. 사용자가 좌표를 준 적이 없는데도 모델이 계획 단계에서 알아서 채운다 — 이것이 단발 응답과 다른 점이다. `maxTurns` 는 루프가 무한히 도는 것을 막는 안전장치로, 비용 관리의 첫 번째 손잡이다.

Python에서는 `ClaudeSDKClient` 로 같은 루프를 연다.

```python
import asyncio
from claude_agent_sdk import ClaudeSDKClient, ClaudeAgentOptions

async def main():
    options = ClaudeAgentOptions(
        mcp_servers={"weather-tools": weather_server},
        allowed_tools=["mcp__weather-tools__get_weather"],
    )
    async with ClaudeSDKClient(options=options) as client:
        await client.query("서울 날씨 알려줘")
        async for msg in client.receive_response():
            print(msg)

asyncio.run(main())
```

## 설치부터 배포까지 — 전체 파이프라인

여기까지가 *동작하는 에이전트*다. 이를 실제 서비스로 올리려면 네 단계의 흐름을 거친다.

![Claude Agent SDK 파이프라인 — 환경 설정·툴 정의·에이전트 루프·배포 4단계](/images/claude-agent-sdk-getting-started/02-pipeline.png)

| 단계 | 핵심 작업 | 체크포인트 |
|------|----------|-----------|
| **1. 설정** | SDK 설치·API 키 환경변수 | 키는 코드에 박지 않는다 |
| **2. 툴 정의** | `tool()` + MCP 서버 | `content` 형식 준수 |
| **3. 루프** | `query` 실행 | `maxTurns` 로 폭주 차단 |
| **4. 배포** | 서버리스·컨테이너 | 키는 시크릿으로 주입 |

배포 단계에서 가장 흔한 실수는 API 키를 빌드에 포함시키는 것이다. Vercel·AWS Lambda 같은 환경에서는 시크릿 매니저로 키를 주입하고, 에이전트가 *쓰기*를 하는 툴(파일·결제·메일)에는 권한을 최소로 묶는다.

## 다음 단계 — 메모리와 멀티에이전트

툴 하나짜리 에이전트가 돌면 절반은 끝난 셈이다. 여기서 작업이 길어지면 **메모리**(이전 결정을 외부 DB에 저장), 역할이 나뉘면 **멀티에이전트**(서브에이전트로 분담)를 붙인다.

![툴 하나가 돈 다음 무엇부터 붙일지 — 메모리·멀티에이전트 확장 결정 흐름](/images/claude-agent-sdk-getting-started/03-flow.png) 이 확장 구조의 큰 그림은 **AI 에이전트 완벽 가이드**의 4요소(툴 호출·메모리·멀티에이전트·MCP)로 정리했다. 노트 기반 메모리를 실제로 붙이는 예는 <Link href="/ko/blog/obsidian-claude-code-mcp">Obsidian + Claude Code MCP 연동</Link>에서, 1인 운영자가 에이전트를 자동화 스택에 끼워 넣는 법은 <Link href="/ko/blog/solo-developer-automation-stack">1인 개발자 자동화 스택</Link>에서 이어진다.

## 자주 묻는 질문 (FAQ)

### Claude Agent SDK는 TypeScript와 Python 중 무엇을 써야 하나요?

기존 코드베이스의 언어를 따르는 것이 가장 합리적이다. 웹·프론트엔드 중심이라면 TypeScript, 데이터·ML 파이프라인 중심이라면 Python이 자연스럽다. 두 SDK는 `tool` 정의와 `query` 실행 구조가 거의 같아 한쪽을 익히면 다른 쪽으로 옮기기 쉽다. 입문 학습용이라면 익숙한 언어를 고르면 된다.

### allowedTools를 지정하지 않으면 어떻게 되나요?

`allowedTools` 는 어떤 툴을 권한 승인 없이 바로 실행할지 지정하는 사전 허용 목록이다. 지정하지 않으면 툴 사용 시 승인 흐름을 거치게 되어, 파괴적 행동을 막는 안전장치로 작동한다. 신뢰할 수 있는 읽기 전용 툴은 허용 목록에 넣어 매끄럽게 돌리고, 쓰기·삭제처럼 위험한 툴은 의도적으로 빼서 승인을 강제하는 설계를 권한다.

### 에이전트가 무한 루프에 빠지면 어떻게 막나요?

`maxTurns` 옵션으로 루프의 최대 반복 횟수를 제한하는 것이 가장 직접적인 방법이다. 입문 단계에서는 3~5 정도로 낮게 두고 동작을 관찰한 뒤 늘리는 편이 안전하다. 더불어 툴 설명을 명확히 써서 모델이 불필요하게 재시도하지 않게 하고, 외부 API 툴에는 타임아웃과 에러 처리를 넣어 루프가 한 곳에서 멈추지 않게 한다.

### 만든 에이전트를 어디에 배포하나요?

서버리스 함수(Vercel·AWS Lambda)나 컨테이너(Docker)가 일반적이다. 핵심은 API 키를 빌드 산출물에 포함하지 말고 환경변수·시크릿 매니저로 런타임에 주입하는 것이다. 에이전트가 외부 시스템에 쓰기를 한다면 부여하는 권한을 최소 범위로 묶고, 호출량과 비용을 모니터링하는 로깅을 함께 붙이면 운영이 안정적이다.

## 마무리

첫 자율 에이전트는 거창하지 않아도 된다. 툴 하나, 루프 한 번이면 *스스로 계획하고 행동하는* 에이전트의 본질을 손으로 확인할 수 있다. 이 글의 `get_weather` 예제를 자기 도메인의 툴로 바꿔 끼우는 순간, 같은 골격이 리서치·코딩·운영 어디에나 적용된다. 작게 시작해 루프 하나를 완성하는 것, 그것이 자율 에이전트로 가는 가장 빠른 길이다.
