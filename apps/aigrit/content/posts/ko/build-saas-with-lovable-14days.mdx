## 한 줄 요약

**[Lovable](https://lovable.dev)**은 화면과 기본 기능을 빠르게 만들어 주지만, 결제 붙은 SaaS에서 시간이 걸리는 곳은 따로 있다. *결제 설정, 데이터 접근 권한, 출시 직전 마무리*다. 이 글은 하루 2~4시간을 쓰는 1인 기준으로 2주 출시 계획을 구간별로 나누고, 각 구간에서 공식 문서로 확인해야 할 것과 흔히 놓치는 점검 항목을 정리한다.

<Callout type="info" title="이 글의 범위">
  개인 출시 기록이 아니라 Lovable 공식 문서(결제·요금·크레딧)를 바탕으로 짠 계획표다. 예시 제품은 "회의록을 붙여넣으면 요약과 할 일을 뽑아 주는 구독형 웹 서비스"로 가정했다. 일정은 목표치이며, 기능 범위에 따라 늘어날 수 있다. 요금·한도는 2026년 10월 확인 기준이다.
</Callout>

어느 도구로 시작할지 아직 정하지 않았다면 <Link href="/ko/blog/nocode-vibe-coding-saas-guide-2026">노코드·바이브 코딩 SaaS 완벽 가이드</Link>에서 도구 지형을 먼저 보고, v0·Bolt와의 차이는 <Link href="/ko/blog/v0-vs-bolt-vs-lovable">v0 vs Bolt vs Lovable 비교</Link>를 참고하자.

## Lovable로 SaaS를 띄울 때 필요한 것

Lovable은 자연어로 지시하면 웹 앱 코드를 만들고, 내장 백엔드인 **Lovable Cloud**로 로그인·데이터베이스를 붙일 수 있다. 결제는 공식 문서 기준 **Stripe와 Paddle** 두 곳을 지원하며 프로젝트당 하나만 켤 수 있고, **Pro 이상 요금제**가 필요하다.

![Lovable로 SaaS를 띄울 때 필요한 구성 — 화면·백엔드·인증·결제·배포와 직접 확인할 항목](/images/build-saas-with-lovable-14days/01-overview.png)

| 구성 | Lovable에서 하는 일 | 직접 확인할 것 |
|------|------|------|
| **화면·기능** | 프롬프트로 생성·수정 | 한 번에 크게 말고 작게 지시 |
| **백엔드·DB** | Lovable Cloud 또는 내 Supabase 프로젝트 | 데이터 접근 정책 |
| **인증** | 이메일·소셜 로그인 | 다른 계정 데이터가 보이지 않는지 |
| **결제** | Stripe 또는 Paddle (Pro 이상) | 판매자 국가 지원 여부, 테스트·라이브 구분 |
| **배포** | 내장 게시·커스텀 도메인 | 메타 태그·OG·sitemap |

출처: [Lovable 결제 문서](https://docs.lovable.dev/features/payments), [Plans and credits](https://docs.lovable.dev/introduction/plans-and-credits). 문서에 따르면 오래된 React + Vite 프로젝트는 결제를 쓰려면 Lovable Cloud가 필요하고, 새 TanStack Start 프로젝트는 결제 데이터를 저장할 때만 데이터베이스(Lovable Cloud 또는 내 Supabase)가 필요하다.

## 2주 계획표 — 구간별로 할 일

![Lovable SaaS 2주 계획 — 기획·초안, 기능·데이터, 결제, 마감·출시 4구간](/images/build-saas-with-lovable-14days/02-two-week-plan.png)

| 구간 | 일정(목표) | 핵심 작업 | 끝났다는 기준 |
|------|------|------|------|
| **기획·초안** | 1~3일 | 한 문장 가치 제안, 화면 3개, 첫 프롬프트 | 핵심 화면이 클릭으로 이어진다 |
| **기능·데이터** | 4~8일 | 핵심 기능, 테이블 설계, 로그인 | 내 데이터만 보인다 |
| **결제** | 9~11일 | 요금제, 체크아웃, 구독 상태 저장 | 테스트 결제가 상태에 반영된다 |
| **마감·출시** | 12~14일 | 반응형, 빈 화면·오류 문구, 도메인 | 라이브 결제 1건이 끝까지 간다 |

### 1~3일 — 기획과 첫 초안

첫 사흘은 코드보다 범위를 정하는 데 쓴다. "회의 녹취를 붙여넣으면 요약과 할 일을 뽑아 주는 서비스"처럼 한 문장으로 가치를 정하고, 랜딩·입력·결과 세 화면만 그린다. 첫 프롬프트에는 화면 구성과 로그인·구독이 필요하다는 사실까지 넣는다. 이후 수정은 "결과 영역에 복사 버튼 추가"처럼 작게 나눠 지시하는 편이 결과를 통제하기 쉽다.

### 4~8일 — 기능과 데이터

사용자 테이블과 요약 기록 테이블을 만들고 로그인을 붙인다. 이 구간에서 가장 중요한 것은 **데이터 접근 정책**이다. 다른 계정으로 로그인했을 때 남의 기록이 보이지 않는지, 로그아웃 상태에서 데이터 요청이 막히는지를 직접 확인하자. AI가 만든 정책 초안은 동작은 해도 범위가 넓게 잡혀 있을 수 있다.

### 9~11일 — 결제

결제는 미리 확인할 조건이 많아 일정을 넉넉히 잡는다.

- **판매자 국가**: 2026년 10월 기준 한국은 [Stripe 가입 가능 국가](https://stripe.com/global) 목록에 없다. Lovable 문서도 한 결제사에서 국가가 지원되지 않으면 다른 결제사를 확인하라고 안내한다. 한국 사업자라면 Paddle의 지원 국가를 먼저 확인하고, 안 되면 국내 PG(토스페이먼츠·포트원)를 별도로 붙이는 방법을 검토하자
- **테스트와 라이브**: 미리보기에서는 테스트 모드로만 동작하고 실제 카드는 결제되지 않는다. 게시한 앱은 라이브 모드이며, 공식 문서의 출시(go-live) 절차를 모두 마쳐야 라이브 결제가 열린다
- **구독 상태 저장**: 결제사 알림(Webhook)을 받아 구독 상태를 DB에 반영하는 흐름이 필요하다. 직접 구성한다면 Webhook 서명 검증을 빠뜨리지 말자

요금제는 처음엔 무료와 유료 하나로 단순하게 시작해도 된다.

### 12~14일 — 마감과 출시

남은 사흘은 모바일 화면, 빈 상태, 오류 문구 같은 마무리에 쓴다. 커스텀 도메인을 연결하고 메타 태그·OG 이미지·sitemap을 채운다. 출시 전에는 라이브 모드에서 결제 한 건을 끝까지 진행해 구독 상태가 반영되는지 확인하고, 필요하면 환불 처리까지 해 본다. 검색 노출용 기본 점검은 <Link href="/ko/blog/adsense-approval-prep-checklist">애드센스 승인 준비 체크리스트</Link>의 사이트 점검 항목을 그대로 써도 된다.

## 결제·보안에서 막히는 지점 — 출시 전 점검표

![출시 전 점검표 — 데이터 접근 정책, 결제사 국가, 테스트·라이브 구분, Webhook 검증, 크레딧](/images/build-saas-with-lovable-14days/03-pitfalls.png)

| 점검 항목 | 왜 문제가 되나 | 확인 방법 |
|------|------|------|
| **데이터 접근 정책** | 정책이 넓으면 다른 사용자 데이터가 노출된다 | 계정 두 개로 교차 확인 |
| **결제사 국가** | 판매자 계정을 못 만들면 결제 자체가 막힌다 | Stripe·Paddle 지원 국가 확인 |
| **테스트·라이브 구분** | 미리보기 결제는 실제로 청구되지 않는다 | 게시 앱에서 라이브 결제 1건 |
| **Webhook 검증** | 위조 요청으로 구독 상태가 바뀔 수 있다 | 서명 검증 코드 확인 |
| **크레딧 소모** | 큰 변경을 한 번에 요청하면 크레딧이 빨리 닳는다 | 작은 단위로 나눠 지시 |

결제와 권한 관련 코드는 AI 출력을 그대로 믿지 말고 사람이 읽어 확인하는 것이 안전하다. 코드를 읽고 고치는 데 익숙해지고 싶다면 <Link href="/ko/blog/claude-code-vs-cursor">Claude Code vs Cursor</Link> 비교에서 IDE·터미널 기반 AI 코딩 도구를 함께 보자.

## 결론 — 2주는 가능한 목표, 결제 구간에 여유를 둔다

<ProCon>
  <Pros>
    - 초안 속도: 화면과 기본 흐름을 프롬프트로 빠르게 만든다
    - 내장 백엔드: Lovable Cloud로 로그인·DB 셋업이 짧다
    - 결제 내장: Stripe·Paddle 중 하나를 프로젝트에 연결
    - 1인 풀스택: 화면·데이터·배포를 한 도구에서 다룬다
  </Pros>
  <Cons>
    - 결제사 조건: 한국은 Stripe 가입 국가가 아니라 대안 확인 필요
    - 보안 검토: 데이터 접근 정책은 사람이 확인해야 한다
    - 크레딧: 큰 변경을 반복하면 빨리 소모된다
    - 마무리: 반응형·빈 상태·오류 처리에 시간이 든다
  </Cons>
</ProCon>

2주는 기능 범위를 좁히면 현실적인 목표다. 다만 결제사 선택과 데이터 접근 정책은 일정이 밀리기 쉬운 구간이니, 계획을 짤 때 이 두 곳에 여유를 두자.

## 자주 묻는 질문 (FAQ)

### Lovable로 2주 안에 결제 붙은 SaaS를 만들 수 있나요?

기능 범위를 좁히면 목표로 삼을 만합니다. 화면과 기본 기능은 프롬프트로 빠르게 만들 수 있고, Lovable Cloud로 로그인·DB를 붙이는 시간도 짧습니다. 다만 결제사 계정 개설, 테스트·라이브 전환, 데이터 접근 정책 점검은 도구가 대신 끝내 주지 않으니 이 구간에 일정 여유를 두세요.

### 코딩을 거의 몰라도 따라 할 수 있나요?

초안과 기본 기능은 자연어 지시만으로 만들 수 있습니다. 하지만 다른 사용자 데이터가 보이지 않게 막는 접근 정책과 결제 알림(Webhook) 처리는 생성된 코드를 읽고 확인해야 안전합니다. 처음 시작은 노코드에 가깝지만, 운영하려면 코드를 읽는 최소한의 능력은 갖추는 편이 좋습니다.

### 한국에서 Lovable 결제 연동은 어떻게 하나요?

2026년 10월 기준 한국은 Stripe 가입 가능 국가 목록에 없습니다. Lovable은 Stripe와 Paddle을 지원하므로 Paddle의 판매자 지원 국가를 먼저 확인하세요. 둘 다 어렵다면 토스페이먼츠·포트원 같은 국내 PG를 별도로 연동하는 방법이 있습니다. 해외 법인이 있다면 Stripe도 선택지가 됩니다.

### 비용은 얼마나 드나요?

무료 요금제는 하루 5 크레딧, 월 30 크레딧까지 쓸 수 있어 초안 단계는 무료로도 시도할 수 있습니다. 결제 기능은 Pro 이상에서만 쓸 수 있고, 요금은 공식 페이지에서 확인해야 합니다. 그 밖에 도메인 비용과 매출이 생길 때의 결제 수수료가 듭니다.

## 마무리

Lovable은 *초안까지의 시간*을 크게 줄여 주지만, 결제와 데이터 권한은 여전히 사람이 챙겨야 한다. 2주 계획을 세운다면 결제사 조건부터 확인하고, 출시 전 점검표를 한 줄씩 지워 가자. 출시 이후 반복 작업을 줄이는 방법은 <Link href="/ko/blog/solo-developer-automation-stack">1인 개발자 자동화 스택</Link>에서 이어 볼 수 있다.
