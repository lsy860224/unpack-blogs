## 한 줄 요약

고객사 문서(매뉴얼·FAQ·약관)를 올리면 *그 내용으로만* 답하는 챗봇을 만들어 월 구독으로 파는 모델이다. 핵심 기술은 **RAG(검색 증강 생성)** — 문서를 조각내 **임베딩**으로 저장하고, 질문이 오면 관련 조각을 **벡터 검색**으로 찾아 LLM에 함께 넣어 답하게 한다. 고객마다 자료가 다르므로, SaaS로 팔 때는 *고객사별 데이터 분리*가 기술만큼 중요하다.

<Callout type="info" title="이 글의 기준">
  예제 스택: Next.js(서버 코드) + Supabase(pgvector) + OpenAI 임베딩 + Claude(답변 생성). 아래 TypeScript 코드는 각 SDK 최신 버전으로 타입 검사를, SQL은 pgvector가 설치된 PostgreSQL에서 실행 확인을 거쳤다. 응답 속도나 정확도 같은 운영 수치는 측정하지 않았고, 비용은 계산 방법으로 정리했다.
</Callout>

챗봇 SaaS는 AI를 새로 만드는 일이 아니라 *이미 있는 LLM에 고객 데이터를 연결해 파는 일*이다. 노코드·바이브 코딩으로 SaaS를 짓는 큰 그림은 <Link href="/ko/blog/nocode-vibe-coding-saas-guide-2026">노코드·바이브 코딩 SaaS 완벽 가이드</Link>에서 다뤘으니, 이 글은 *RAG 파이프라인을 코드로 구현하고 상품화하는 부분*에 집중한다.

## RAG 파이프라인 — 문서가 답변이 되기까지

![RAG 파이프라인 — 문서 분할, 임베딩, 저장, 검색, 생성](/images/build-rag-chatbot-saas/01-pipeline.png)

RAG는 두 흐름으로 나뉜다. 문서가 올라올 때 한 번 하는 **인덱싱**과, 질문이 올 때마다 하는 **질의응답**이다.

1. **분할** — PDF·문서를 의미 단위 조각으로 자른다 (문단·제목 기준이 무난하다)
2. **임베딩** — 각 조각을 벡터로 바꾼다
3. **저장** — 벡터를 고객사(테넌트) 표시와 함께 DB에 넣는다
4. **검색** — 질문을 임베딩해 *같은 테넌트*의 가까운 조각 몇 개를 찾는다
5. **생성** — 찾은 조각과 질문을 LLM에 넣어 출처 번호가 달린 답을 만든다

다섯 단계 중 *검색 품질*이 답변 품질을 가장 크게 좌우한다. LLM이 좋아도 엉뚱한 조각을 가져오면 답이 틀리기 때문에, 조각 크기와 검색 개수를 실제 문서로 시험하며 조정하는 게 핵심 작업이다.

## 1) 데이터베이스 — 테넌트를 나누는 스키마

Supabase는 PostgreSQL에 [pgvector](https://supabase.com/docs/guides/ai) 확장을 제공한다. 고객사별로 데이터가 섞이지 않도록 `tenant_id`를 두고, 검색 함수에서 반드시 그 값으로 거른다.

```sql
create extension if not exists vector;

create table documents (
  id bigint generated always as identity primary key,
  tenant_id text not null,
  source text not null,
  content text not null,
  embedding vector(1536) not null
);

create index on documents using hnsw (embedding vector_cosine_ops);
create index on documents (tenant_id);
alter table documents enable row level security;

create or replace function match_documents(
  query_embedding vector(1536),
  match_tenant text,
  match_count int
)
returns table (id bigint, content text, source text, similarity float)
language sql stable as $$
  select id, content, source, 1 - (embedding <=> query_embedding) as similarity
  from documents
  where tenant_id = match_tenant
  order by embedding <=> query_embedding
  limit match_count;
$$;
```

`<=>`는 코사인 거리 연산자이고, `1 - 거리`를 유사도로 돌려준다. 행 수준 보안(RLS)을 켜 두면 브라우저용 키로는 이 테이블을 직접 읽을 수 없고, 아래 코드처럼 서버에서 서비스 키로만 접근하게 된다. 테넌트가 많아지면 HNSW 인덱스와 `where` 필터가 함께 쓰일 때 결과가 요청 개수보다 적게 나올 수 있으므로, 사용하는 pgvector 버전의 필터링 옵션을 공식 문서에서 확인하자.

## 2) 서버 코드 — 인덱싱과 답변

아래는 인덱싱(조각 저장)과 답변(검색 + 생성)을 하나로 묶은 서버 코드다. 서비스 키와 API 키는 서버 환경 변수로만 두고 브라우저로 보내지 않는다.

```typescript
// lib/rag.ts — 서버에서만 실행 (서비스 키는 브라우저로 보내지 않는다)
import OpenAI from "openai";
import Anthropic from "@anthropic-ai/sdk";
import { createClient } from "@supabase/supabase-js";

const openai = new OpenAI(); // OPENAI_API_KEY
const anthropic = new Anthropic(); // ANTHROPIC_API_KEY
const supabase = createClient(
  process.env.SUPABASE_URL!,
  process.env.SUPABASE_SERVICE_ROLE_KEY!,
);

const EMBED_MODEL = "text-embedding-3-small"; // 1536차원

interface Match {
  id: number;
  content: string;
  source: string;
  similarity: number;
}

// 1) 인덱싱: 문서 조각을 한 번에 임베딩해 테넌트별로 저장
export async function indexChunks(
  tenantId: string,
  source: string,
  chunks: string[],
): Promise<void> {
  const { data } = await openai.embeddings.create({ model: EMBED_MODEL, input: chunks });
  const rows = data.map((d, i) => ({
    tenant_id: tenantId,
    source,
    content: chunks[i],
    embedding: d.embedding,
  }));
  const { error } = await supabase.from("documents").insert(rows);
  if (error) throw error;
}

// 2) 검색 + 3) 생성: 같은 테넌트의 문서에서만 찾아 근거로 답한다
export async function answer(tenantId: string, question: string): Promise<string> {
  const { data: q } = await openai.embeddings.create({ model: EMBED_MODEL, input: question });

  const { data, error } = await supabase.rpc("match_documents", {
    query_embedding: q[0].embedding,
    match_tenant: tenantId,
    match_count: 5,
  });
  if (error) throw error;
  const matches = (data ?? []) as Match[];
  if (matches.length === 0) return "자료에서 찾지 못했습니다.";

  const context = matches
    .map((m, i) => `[${i + 1}] (${m.source})\n${m.content}`)
    .join("\n---\n");

  const msg = await anthropic.messages.create({
    model: "claude-sonnet-5-5", // 최신 모델 ID는 공식 문서에서 확인
    max_tokens: 1024,
    system:
      "주어진 자료에 근거해서만 답하라. 자료에 없으면 '자료에서 찾지 못했습니다'라고 답하라. " +
      "답의 근거가 된 자료 번호를 [1]처럼 문장 끝에 표시하라.",
    messages: [{ role: "user", content: `자료:\n${context}\n\n질문: ${question}` }],
  });

  return msg.content
    .map((block) => (block.type === "text" ? block.text : ""))
    .join("");
}
```

`tenantId`는 *요청 본문에서 그대로 받지 말고*, 로그인 세션이나 위젯 API 키에서 서버가 결정해야 한다. 그래야 다른 고객사의 문서를 조회하는 요청을 막을 수 있다. 에이전트처럼 도구 호출·여러 단계 추론까지 붙이려면 <Link href="/ko/blog/claude-agent-sdk-getting-started">Claude Agent SDK 입문</Link>의 구조로 확장하면 되고, 인증·스토리지까지 포함한 백엔드 전체는 <Link href="/ko/blog/supabase-ai-saas-backend">Supabase + AI SaaS 백엔드</Link>에 정리했다.

## 벡터 DB 고르기 — 어디에 저장할까

![벡터 DB 선택 — Supabase pgvector, Pinecone, Qdrant의 형태와 잘 맞는 상황](/images/build-rag-chatbot-saas/02-overview.png)

| 항목 | Supabase pgvector | Pinecone | Qdrant |
|------|-------------------|----------|--------|
| **형태** | Postgres 확장 | 관리형 벡터 DB | 오픈소스(셀프호스트) + 클라우드 |
| **장점** | 인증·DB·스토리지와 한 프로젝트 | 벡터 검색 전용, 운영 부담 적음 | 내 서버에 데이터 보관 가능 |
| **잘 맞는 상황** | MVP, 이미 Supabase를 쓰는 경우 | 벡터 규모가 커지고 검색을 분리할 때 | 데이터를 외부에 둘 수 없는 고객 |
| **요금** | 무료 플랜, Pro $25부터 | 사용량 기반, 공식 확인 | 셀프호스트 무료, 클라우드는 공식 확인 |

초기 MVP라면 Supabase pgvector가 가장 간단하다. 인증·DB·스토리지가 한곳에 있어 챗봇 SaaS의 백엔드를 통째로 올릴 수 있다. 벡터 규모가 커져 검색만 따로 운영하고 싶다면 [Pinecone](https://www.pinecone.io) 같은 전용 서비스로 그 부분만 옮기고, 데이터를 외부 클라우드에 둘 수 없는 고객이라면 [Qdrant](https://qdrant.tech) 셀프호스트를 검토하자.

## 비용 — 대부분은 답변 생성에서 나온다

![RAG 챗봇 비용 구조 — 인덱싱, 질문 임베딩, 검색, 답변 생성](/images/build-rag-chatbot-saas/03-cost.png)

비용은 단계별 토큰 양에 공식 단가를 곱해 계산한다. 단가는 자주 바뀌므로 OpenAI·Anthropic 요금 페이지의 현재 값을 넣자.

| 단계 | 언제 | 비용 계산 |
|------|------|------|
| 인덱싱 임베딩 | 문서가 올라올 때 1회 | 문서 전체 토큰 × 임베딩 단가 |
| 질문 임베딩 | 질문마다 | 질문 토큰 × 임베딩 단가 |
| 검색 | 질문마다 | DB 요금에 포함 |
| 답변 생성 | 질문마다 | (자료 조각 + 질문) 입력 토큰 × 입력 단가 + 답변 토큰 × 출력 단가 |

일반적으로 임베딩 단가는 생성 모델보다 훨씬 낮고, 매 질문마다 자료 조각 몇 개를 함께 넣는 *답변 생성*이 변동비의 대부분을 차지한다. 그래서 검색 개수를 무작정 늘리면 비용이 같이 늘어난다. 고객사당 구독료는 *예상 질문 수 × 질문당 생성 비용* 위에 마진을 얹어 설계하고, 질문량 상한과 초과분 과금을 두는 편이 안전하다. 구독·결제 구조는 <Link href="/ko/blog/solo-saas-pricing-payments">1인 SaaS 가격 책정·결제 붙이기</Link>에서 다뤘다.

## 상품화 — 챗봇을 SaaS로 파는 세 가지 모델

### 웹사이트 위젯 모델

- 고객사 사이트에 스크립트 한 줄로 챗봇 위젯을 띄운다
- 고객사별 위젯 키로 `tenantId`를 서버에서 결정한다
- 월 구독 + 질문량 초과분 과금 구조가 흔하다

### 사내 지식봇 모델

- 사내 위키·매뉴얼을 넣고 직원 질문에 답한다
- 보안 요구가 높아 데이터 보관 위치(셀프호스트 등)를 묻는 경우가 많다
- 좌석당 과금이 잘 맞는다

### 메신저 연동 모델

- Slack·Discord에 봇으로 붙여 채널 안에서 응대한다
- 별도 화면 없이 기존 협업 도구 안에서 동작한다

메신저 봇의 구체적인 구현은 <Link href="/ko/blog/claude-discord-slack-bot">Claude 디스코드·슬랙 봇 만들기</Link>에서 다뤘다.

## 결론 — 기술은 단순, 차별점은 데이터와 분리

<ProCon>
  <Pros>
    - 코드 구조가 단순: 인덱싱·검색·생성 세 부분
    - 모델 학습 없이 API로 구현, 고객 문서만 바꿔 여러 고객에 판매
    - Supabase로 MVP 백엔드를 한 프로젝트에 구성
  </Pros>
  <Cons>
    - 검색 품질이 답변 품질을 좌우해 문서 정제·조각 크기 조정이 필요
    - 고객사 데이터 분리·보안 설계가 필수
    - 답변 생성 비용이 질문 수에 비례해 늘어남
  </Cons>
</ProCon>

RAG 챗봇의 코드는 세 조각으로 단순하다. 진짜 차별점은 *고객마다 다른 문서를 얼마나 잘 정리해 넣느냐*와 *그 데이터를 얼마나 안전하게 분리하느냐*에서 나온다. 출처를 강제하고 근거를 검증하는 설계는 <Link href="/ko/blog/ai-agent-research-automation">AI 에이전트 리서치 자동화</Link>의 근거 카드 방식과도 통한다.

## 자주 묻는 질문 (FAQ)

### RAG 챗봇을 만들려면 머신러닝 지식이 필요한가요?

필요하지 않습니다. 임베딩과 답변 생성은 모두 API로 호출하므로 모델을 직접 학습시키지 않습니다. 필요한 건 문서를 조각내고, 데이터베이스에 저장하고, 검색 결과를 LLM에 넣는 일반적인 백엔드 개발 능력입니다. 나머지는 인증·결제 같은 평범한 SaaS 작업입니다.

### 환각(없는 내용을 지어내는 답변)은 어떻게 줄이나요?

시스템 프롬프트에 "자료에 없으면 모른다고 답하라"를 명시하고, 답변에 근거 자료 번호를 달게 해 사용자가 확인할 수 있게 하세요. 그래도 검색이 엉뚱한 조각을 가져오면 답이 틀리므로, 실제 고객 질문 목록으로 조각 크기와 검색 개수를 시험하며 조정하는 것이 가장 효과적입니다.

### 고객사 데이터가 섞이지 않게 하려면 어떻게 하나요?

모든 조각에 고객사 식별자(tenant_id)를 저장하고, 검색 함수가 항상 그 값으로 거르게 하세요. 식별자는 요청 본문에서 받지 말고 로그인 세션이나 위젯 키로 서버가 정해야 합니다. 테이블에는 행 수준 보안을 켜고, 서비스 키는 서버 환경 변수로만 보관하세요.

### 벡터 DB는 무엇으로 시작하는 게 좋나요?

이미 Supabase를 쓰거나 MVP를 빠르게 세우려면 Supabase pgvector가 간단합니다. 인증·DB·스토리지와 같은 프로젝트에서 관리할 수 있고 SQL 함수 하나로 검색이 끝납니다. 벡터 규모가 커지거나 데이터를 외부에 둘 수 없는 고객을 받게 되면 Pinecone이나 Qdrant로 그 부분만 옮기는 순서가 안전합니다.
