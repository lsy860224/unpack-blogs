## 한 줄 요약

고객사 문서(매뉴얼·FAQ·약관)를 올리면 그 내용으로만 답하는 챗봇을 만들어 월 구독으로 파는 모델이다. 핵심 기술은 **RAG(Retrieval-Augmented Generation)** — 문서를 잘게 쪼개 **임베딩**으로 저장하고, 질문이 오면 관련 조각을 **벡터 검색**으로 찾아 LLM에 함께 넣어 답을 만든다. 환각을 줄이고 "우리 문서 기반"이라는 차별점이 생겨, 고객마다 자료가 다른 B2B SaaS로 팔기 좋다.

<Callout type="info" title="구현 환경">
  스택: Next.js(프론트·API) + Supabase(pgvector) + OpenAI Embeddings + Claude(생성) · 기준일: 2027년 7월 · 테스트 문서: 약 80페이지 PDF 매뉴얼 1건 · 측정: 임베딩 비용, 질문당 응답 시간, 답변 정확도(출처 일치 여부) · 비교 백엔드: Supabase pgvector / Pinecone / 셀프호스트 Qdrant
</Callout>

챗봇 SaaS는 "AI를 새로 만드는 일"이 아니라 *기존 LLM에 고객 데이터를 연결해 파는 일*이다. 노코드·바이브 코딩으로 SaaS를 짓는 큰 그림은 <Link href="/ko/blog/nocode-vibe-coding-saas-guide-2026">노코드 바이브 코딩 SaaS 가이드</Link>에서 다뤘으니, 이 글은 *RAG 파이프라인을 코드로 구현하고 상품화하는 부분*에 집중한다.

## RAG 파이프라인 — 문서가 답변이 되기까지

![문서 업로드에서 출처 표기 답변까지 — 임베딩·저장·검색·생성 RAG 파이프라인](/images/build-rag-chatbot-saas/01-pipeline.png)

RAG는 크게 두 흐름으로 나뉜다. **사전 처리(인덱싱)** 와 **질의 응답(런타임)** 이다. 인덱싱은 문서가 올라올 때 한 번, 응답은 질문이 올 때마다 일어난다.

1. **문서 분할(Chunking)**: PDF·문서를 500~1000자 단위 조각으로 자르기
2. **임베딩(Embedding)**: 각 조각을 벡터로 변환해 의미를 좌표로 표현
3. **저장(Vector DB)**: 벡터를 pgvector 등 벡터 DB에 적재
4. **검색(Retrieval)**: 질문을 임베딩해 가장 가까운 조각 N개를 찾기
5. **생성(Generation)**: 찾은 조각 + 질문을 LLM에 넣어 출처 포함 답변 생성

이 다섯 단계 중 *검색 품질*이 답변 품질의 8할을 결정한다. LLM이 아무리 좋아도 엉뚱한 조각을 가져오면 답이 틀리기 때문에, 분할 크기와 검색 개수(N)를 데이터에 맞춰 조정하는 게 핵심 작업이다.

## 핵심 구현 — 임베딩·검색·생성 코드

먼저 문서 조각을 임베딩해 Supabase에 저장하는 인덱싱 단계다. `pgvector` 확장을 켜고 벡터 컬럼을 둔 테이블에 적재한다.

```typescript
// 1) 인덱싱: 문서 조각 → 임베딩 → Supabase 저장
import OpenAI from "openai";
import { createClient } from "@supabase/supabase-js";

const openai = new OpenAI();
const supabase = createClient(process.env.SUPABASE_URL!, process.env.SUPABASE_KEY!);

async function indexChunks(chunks: { id: string; text: string }[]) {
  for (const chunk of chunks) {
    const { data } = await openai.embeddings.create({
      model: "text-embedding-3-small",
      input: chunk.text,
    });
    await supabase.from("documents").insert({
      content: chunk.text,
      embedding: data[0].embedding, // vector(1536) 컬럼
    });
  }
}
```

질문이 오면 같은 모델로 질문을 임베딩하고, 코사인 거리로 가장 가까운 조각을 가져온다. 검색은 Postgres 함수로 두면 한 번의 RPC로 끝난다.

```sql
-- 2) 검색: pgvector 코사인 유사도 Top-N
create function match_documents(query_embedding vector(1536), match_count int)
returns table (content text, similarity float)
language sql stable as $$
  select content, 1 - (embedding <=> query_embedding) as similarity
  from documents
  order by embedding <=> query_embedding
  limit match_count;
$$;
```

마지막으로 찾은 조각을 컨텍스트로 묶어 LLM에 넣고, "주어진 자료 밖이면 모른다고 답하라"는 지시로 환각을 막는다.

```typescript
// 3) 생성: 검색된 조각 + 질문 → 답변 (출처 기반)
const { data: docs } = await supabase.rpc("match_documents", {
  query_embedding: questionEmbedding,
  match_count: 5,
});
const context = docs.map((d) => d.content).join("\n---\n");

const answer = await anthropic.messages.create({
  model: "claude-sonnet-4-5",
  max_tokens: 1024,
  system: "다음 자료에 근거해서만 답하라. 자료에 없으면 '자료에서 찾지 못했습니다'라고 답하라.",
  messages: [{ role: "user", content: `자료:\n${context}\n\n질문: ${question}` }],
});
```

이 세 조각이 RAG의 전부다. 에이전트형으로 도구 호출·다단계 추론까지 붙이려면 <Link href="/ko/blog/claude-agent-sdk-getting-started">Claude Agent SDK 시작하기</Link>에서 다룬 구조로 확장하면 된다. 백엔드를 Supabase로 통째로 세우는 실전은 <Link href="/ko/blog/supabase-ai-saas-backend">Supabase AI SaaS 백엔드</Link>에 정리돼 있다.

## 벡터 DB 비교 — 어디에 저장할까

![RAG 벡터 DB 개요 비교 — 무료 한도·관리 부담·확장성·가격 한눈에](/images/build-rag-chatbot-saas/02-overview.png)

저장소 선택이 초기 비용과 운영 부담을 좌우한다. 세 가지가 흔한 선택지다.

| 항목 | Supabase pgvector | Pinecone | Qdrant |
|------|-------------------|----------|--------|
| **형태** | Postgres 확장 | 호스팅 SaaS | 셀프호스트 + 클라우드 |
| **셋업 난이도** | 낮음(SQL 한 줄) | 낮음 | 중간(Docker) |
| **무료 한도** | DB 용량 내 무료 | 약 1개 인덱스 | 셀프호스트 무제한 |
| **백엔드 통합** | 인증·DB·스토리지 일체 | 별도 연동 | 별도 연동 |
| **확장성** | 중대형까지 | 대규모 특화 | 대규모 가능 |
| **유료 시작가** | 약 $25/월(Pro) | 약 $50/월 | 셀프호스트 무료 |
| **데이터 통제** | 내 프로젝트 DB | 클라우드 위탁 | 내 서버 보관 |

초기 MVP라면 [Supabase](https://supabase.com/docs/guides/ai)의 pgvector가 압도적으로 편하다. 인증·DB·스토리지가 한 프로젝트에 있어 챗봇 SaaS의 백엔드를 통째로 올릴 수 있다. 수십만 벡터를 넘어 검색 지연이 문제가 되면 [Pinecone](https://www.pinecone.io)처럼 벡터 전용 SaaS로 그 부분만 분리하고, 데이터를 외부에 넘기면 안 되는 고객사 대상이면 [Qdrant](https://qdrant.tech) 셀프호스트로 통제권을 가져온다.

## 비용·성능 흐름 — 문서 1건 기준

80페이지 PDF 1건을 인덱싱하고 월 1,000건 질문을 처리할 때의 대략적인 비용·시간이다. 모델 단가는 변동되므로 추세를 보는 용도로만 참고한다.

| 단계 | 처리량 | 비용/시간(대략) |
|------|:------:|:------:|
| 임베딩(인덱싱 1회) | 약 200 조각 | 약 $0.01 |
| 질문 임베딩 | 1,000건 | 약 $0.05 |
| 검색(pgvector) | 1,000건 | 질문당 약 50ms |
| 답변 생성(LLM) | 1,000건 | 약 $3~8 |
| **월 변동비 합계** | — | **약 $3~8** |

핵심은 *변동비 대부분이 답변 생성(LLM)* 에 몰린다는 점이다. 임베딩과 검색은 거의 공짜에 가깝다. 그래서 고객사당 월 구독료를 LLM 호출 비용 위에 충분한 마진으로 얹는 가격 설계가 곧 수익성을 결정한다. 구독·결제 구조는 <Link href="/ko/blog/solo-saas-pricing-payments">솔로 SaaS 가격·결제</Link>에서 단가표와 함께 다뤘다.

## 벡터 DB 점수표 — 5개 축 종합

각 축 5점 기준, 챗봇 SaaS의 MVP 관점에서 세 벡터 DB를 비교한 상대 점수다. 절대 평가가 아니라 *같은 챗봇을 세 백엔드로 올린다고 가정한* 인상치다.

![Supabase·Pinecone·Qdrant 5개 축 종합 점수 — 셋업·통합·확장·통제·가성비](/images/build-rag-chatbot-saas/03-scores.png)

| 축 | Supabase pgvector | Pinecone | Qdrant |
|------|:------:|:----:|:---:|
| 셋업 편의 | 5 | 4 | 3 |
| 백엔드 통합 | 5 | 2 | 2 |
| 대규모 확장 | 3 | 5 | 5 |
| 데이터 통제 | 4 | 2 | 5 |
| 가성비 | 5 | 3 | 4 |
| **합계(25점)** | **22** | **16** | **19** |

합계만 보면 **Supabase**가 앞서지만, 이 점수는 초기 MVP 관점이다. 벡터가 수백만 단위로 커지면 대규모 검색에 특화된 Pinecone이, 데이터 통제가 절대 조건이면 Qdrant 셀프호스트가 역전한다. 시작은 Supabase, 한계가 보일 때 갈아타는 순서가 안전하다.

## 상품화 — 챗봇을 SaaS로 파는 법

### B2B 위젯 임베드 모델

- **고객사 사이트에 스크립트 한 줄** 삽입 → 챗봇 위젯 노출
- 고객사별 문서를 분리 저장(테넌트 격리)해 답변이 섞이지 않게
- 월 구독 + 질문량 초과분 종량 과금이 흔한 구조

### 내부 지식봇(사내 헬프데스크) 모델

- 사내 위키·매뉴얼을 임베딩해 직원 질문에 답하는 봇
- 보안이 중요해 셀프호스트 벡터 DB 수요가 큼
- 좌석당 과금(per-seat)이 잘 맞음

### 메신저 연동 모델

- Slack·Discord에 봇으로 붙여 채널에서 바로 응대
- 별도 UI 없이 기존 협업 도구 안에서 동작
- 봇 연동 자체는 어렵지 않음

메신저로 붙이는 구체적 구현은 <Link href="/ko/blog/claude-discord-slack-bot">Claude Discord·Slack 봇</Link>에서 토큰 발급부터 배포까지 다뤘다.

## 결론 — 기술은 단순, 차별점은 데이터

<ProCon>
  <Pros>
    - Supabase pgvector: 백엔드 일체형, MVP 셋업이 가장 빠름
    - Pinecone: 대규모 벡터에서 검색 지연이 작음
    - Qdrant: 셀프호스트로 데이터 통제, 보안 민감 고객에 강함
  </Pros>
  <Cons>
    - Supabase pgvector: 초대규모에서 전용 DB 대비 튜닝 한계
    - Pinecone: 데이터가 외부 클라우드 경유, 비용이 빨리 늘 수 있음
    - Qdrant: 셀프호스트 운영(업데이트·백업) 부담
  </Cons>
</ProCon>

RAG 챗봇의 코드 자체는 임베딩·검색·생성 세 조각으로 단순하다. 진짜 차별점은 *고객마다 다른 문서 데이터*에서 나온다. 같은 엔진이라도 어떤 자료를 잘 정제해 넣느냐에 따라 답변 품질이 갈리고, 그게 곧 가격을 정당화한다. MVP는 Supabase로 가장 빠르게 세우고, 검색 품질을 데이터에 맞춰 다듬은 뒤, 고객 유형에 맞는 상품 모델을 고르면 된다. 더 넓은 도구 지형은 <Link href="/ko/blog/ai-tools-2026-guide">2026 AI 도구 완벽 가이드</Link>에서 확인할 수 있다.

## 자주 묻는 질문 (FAQ)

### RAG 챗봇을 만들려면 머신러닝 전공 지식이 필요한가요?

필요 없다. 임베딩·생성 모델은 모두 API로 호출하므로, 직접 모델을 학습시키는 일은 없다. 필요한 건 문서를 잘게 쪼개고, 벡터 DB에 저장하고, 검색 결과를 LLM에 넣는 일반적인 백엔드 개발 능력이다. 이 글의 세 코드 조각(인덱싱·검색·생성)이 사실상 전체 구조이며, 나머지는 인증·결제 같은 평범한 SaaS 작업이다.

### 환각(없는 내용을 지어내는 답변)은 어떻게 막나요?

두 가지로 막는다. 첫째, 시스템 프롬프트에 "주어진 자료에 없으면 모른다고 답하라"를 명시해 LLM이 추측하지 않게 한다. 둘째, 답변에 출처 조각을 함께 표시해 사용자가 근거를 확인할 수 있게 한다. 그래도 검색이 엉뚱한 조각을 가져오면 답이 틀리므로, 분할 크기와 검색 개수(N)를 실제 문서로 튜닝하는 게 가장 효과적인 방어다.

### 벡터 DB는 처음에 무엇으로 시작하는 게 좋나요?

Supabase pgvector를 권한다. 인증·DB·스토리지가 한 프로젝트에 들어 있어 챗봇 SaaS 백엔드를 통째로 올릴 수 있고, SQL 함수 하나로 벡터 검색이 끝난다. 수십만 벡터를 넘어 검색 지연이 문제가 되거나, 데이터를 외부에 두면 안 되는 고객사를 받게 되었을 때 Pinecone이나 Qdrant로 그 부분만 분리하는 순서가 안전하다.

### 챗봇 SaaS는 어떻게 수익을 내나요?

변동비 대부분이 답변 생성(LLM 호출)에 몰리고 임베딩·검색은 거의 공짜이므로, 고객사당 월 구독료를 LLM 비용 위에 충분한 마진으로 얹는 구조가 기본이다. B2B 위젯은 월 구독+초과 종량, 사내 지식봇은 좌석당 과금이 잘 맞는다. 핵심은 질문량 상한을 두고 초과분을 종량으로 받아, 헤비 유저가 마진을 잠식하지 않게 설계하는 것이다.
