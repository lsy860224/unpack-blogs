**결론부터: Claude로 짠 블로그 워크플로우의 핵심은 도구 통합이지 도구 자체가 아니다. 단계를 줄이고 사람이 확인할 지점을 분명히 하면 운영에 드는 손이 크게 준다.**

블로그 1편에는 키워드 조사·구조·초안·OG 이미지·내부 링크·성과 추적이 따라옵니다. 1인 운영자가 매일 손으로 거치면 글보다 운영에 시간이 더 들어갑니다. 이 글은 Claude Desktop·Claude Code·Obsidian·GSC·IndexNow를 한 줄로 엮어 이 블로그를 운영하며 정착시킨 SOP입니다. 전체 흐름은 **초안 → 발행 → 색인 → 추적** 4단계로 직선화되어 있고, 각 단계는 도구 1~2개로 닫혀 있어 다음 단계로 전달되는 산출물이 1개뿐입니다.

## 워크플로우 4단계 한눈 — 초안·발행·색인·추적

블로그 운영을 4단계로 쪼개고 각 단계에 도구 1~2개만 배치합니다. 단계가 늘수록 깨질 확률이 커지므로 단계 자체를 줄이는 것이 자동화의 첫 원칙입니다.

| 단계 | 도구 | 산출물 | 사람이 확인할 것 |
|---|---|---|---|
| 1. 초안 | Claude Desktop / Claude Code | MDX 초안 | 사실·출처·본인 경험 여부 |
| 2. 발행 | Git + Vercel + IndexNow | 라이브 URL | 빌드 통과·이미지·링크 |
| 3. 색인 | GSC URL 검사 | 색인 상태 | 누락 원인 |
| 4. 추적 | Obsidian + GSC export | 다음 글 후보 | 우선순위 판단 |

RSS·sitemap 갱신은 빌드가, OG 이미지는 발행 전 스크립트가 처리합니다. 사람 손이 닿는 지점은 표의 오른쪽 열입니다. 같은 사고를 다른 작업으로 확장한 사례는 <Link href="/ko/blog/solo-developer-automation-stack">1인 개발자 자동화 스택 10가지</Link>에 모았습니다. 정적 사이트(Next.js·Astro·Hugo) 전제지만 워드프레스·노션 호스팅에서는 git push 자리에 webhook이 들어갈 뿐 구조는 같습니다.

## Step 1: Claude로 초안 — 키워드 → 구조 → FAQ

초안 단계는 Claude Desktop과 Claude Code의 역할 분담이 핵심입니다. Claude Desktop은 [Anthropic 공식 앱](https://claude.ai/download)으로 MCP 연결과 긴 대화에 편하고, [Claude Code](https://code.claude.com/docs/en/overview)는 터미널에서 파일과 git을 직접 다룹니다. 결과적으로 "구조 잡기와 검색 의도 분석"은 Desktop, "본문 생성과 파일 쓰기"는 Code로 분리되어 한 채팅 안에서 둘이 섞이지 않습니다.

순서는 이렇습니다.

1. **키워드 입력 — Claude Desktop**: GSC에서 노출은 있지만 클릭이 적은 쿼리 1개를 가져와 "이 키워드로 H2 5~7개와 FAQ 3개 구조를 제안해줘"로 시작합니다.
2. **본문 초안 — Claude Code**: 합의된 구조를 `.md`에 적어두고 "이 구조 그대로 본문 2,500자, 톤은 기존 글 3편 참고"로 지시합니다. 기존 글 경로를 컨텍스트에 넣으면 톤·문장 길이가 맞춰집니다.
3. **FAQ 정리**: 본문 완성 후 "독자가 실제로 물을 질문 3~5개로 FAQ를 만들어줘"로 마무리합니다. 참고로 Google은 2023년부터 FAQ 리치 결과를 정부·보건 분야의 권위 있는 사이트 위주로만 보여 주므로, FAQ는 검색 결과 노출보다 독자의 궁금증을 정리하는 용도로 보는 편이 맞습니다.

여기까지가 AI가 도와주는 부분입니다. 문서 안에서 AI를 쓰는 다른 방식은 <Link href="/ko/blog/notion-ai-guide">Notion AI 활용법</Link>에 있습니다. 나머지는 사람이 합니다 — 수치와 사실을 원 출처에서 확인하고, 본인이 실제로 해 본 경험만 경험으로 쓰고, 문장을 다듬는 일입니다. AI가 쓴 "직접 해 봤다"는 문장을 그대로 두면 확인할 수 없는 주장이 됩니다. 이 블로그가 그 원칙을 정한 이유는 <Link href="/ko/blog/hello-world">AIGrit 리뷰 원칙</Link>에 적었습니다.

## Step 2: Git → Vercel 자동 발행 + IndexNow ping

발행은 git push 한 번입니다. `apps/{블로그}/content/posts/`에 MDX를 넣고 커밋하면 Vercel이 빌드해 라이브로 올립니다. 참고로 Vercel의 무료 Hobby 플랜은 개인·비상업 용도로 제한되므로, 광고나 제휴 수익이 있는 블로그라면 Pro 플랜 조건을 확인하세요. 파이프라인 순서는 **로컬 commit → GitHub push → Vercel 빌드 트리거 → CDN 배포 → 발행 hook**으로, 사람이 손대는 지점은 commit 메시지 한 줄뿐입니다.

발행 직후 자동으로 도는 작업은 4가지입니다.

- **OG 카드 준비**: `public/images/{slug}/og.png`를 발행 전에 스크립트로 만들어 둡니다. 사이트별 브랜드 컬러와 글 제목이 들어간 템플릿을 쓰면 수동 작업이 줄어듭니다.
- **sitemap·RSS 갱신**: Next.js의 `sitemap.ts`가 새 MDX를 감지해 `<lastmod>`를 자동 갱신합니다.
- **IndexNow ping**: [IndexNow](https://www.indexnow.org/)로 새 URL을 Bing·Yandex 등 참여 검색엔진에 알립니다. Google은 IndexNow를 쓰지 않으므로 별도 절차가 필요합니다.
- **색인 확인 목록 추가**: 커밋 메시지가 `post:`로 시작하면 새 URL을 색인 확인 목록에 올려 둡니다.

Google [Indexing API](https://developers.google.com/search/apis/indexing-api/v3/quickstart)는 공식적으로 채용 공고(JobPosting)와 라이브 스트림(BroadcastEvent) 페이지에만 쓰도록 안내돼 있습니다. 그래서 일반 블로그 글은 sitemap 제출과 URL 검사로 상태를 확인하고, 색인은 Google이 처리하도록 둡니다. 모바일에서 시작하는 보조 작업은 <Link href="/ko/blog/apple-shortcuts-ai-automation">Apple 단축어 AI 자동화</Link>로 확장할 수 있습니다.

## Step 3: GSC 색인 자동 모니터링 — Obsidian 대시보드 활용

발행했다고 끝이 아닙니다. 색인까지 걸리는 시간은 사이트와 글마다 다르고, 누락이 생겨도 추적하지 않으면 모르고 지나갑니다. Obsidian을 SEO 관제실로 두는 이유입니다. 관제실의 핵심 지표는 **발행 → 색인 대기 → 색인 완료 → 누락 알림** 4상태와, 글별 GSC 노출·클릭·CTR 3개 숫자뿐 — 이 6개만 매일 보면 됩니다.

vault 안에 글마다 노트 1개씩 만들고 frontmatter에 status·indexed_at·target_query를 적습니다. 자동화한다면 이런 작업을 정기적으로 돌리는 구성이 됩니다.

- 최근 발행한 글에 Search Console URL Inspection API로 색인 상태 조회
- 색인되면 indexed_at 기록, 일정 기간이 지나도 색인되지 않으면 확인 목록에 표시
- Obsidian Dataview가 "발행됨 / 색인됨 / 누락" 3개 카운터를 새로고침

Notion·Sheets도 후보지만 Obsidian을 고른 이유는 로컬 마크다운 파일이라 Claude Code가 별도 연동 없이 직접 읽고 수정할 수 있기 때문입니다. 도입은 <Link href="/ko/blog/obsidian-getting-started">Obsidian 시작 가이드</Link>, MCP 서버 적재가 부담된다면 <Link href="/ko/blog/claude-mcp-guide">Claude MCP 가이드</Link>의 최소 구성 패턴을 권장합니다.

## Step 4: 주간 GSC 분석으로 다음 글 결정

이 루틴의 가장 큰 효과는 "다음에 뭘 쓸까"를 감이 아니라 데이터로 정하게 된다는 점입니다. GSC 주간 export를 Claude에 넘기면 다음 글 후보를 정리해 줍니다.

월요일 아침 루틴은 이렇습니다.

1. GSC에서 지난 7일 쿼리·페이지 export(CSV)를 받아 vault에 저장합니다.
2. Claude Desktop에 "노출 100회 이상이면서 클릭률 1% 미만인 쿼리 10개를 뽑고, 기존 글로 커버되는 건 글 ID, 신규 글이 필요한 건 키워드만"이라고 묻습니다.
3. 보강 글과 신규 슬롯이 1주 분량(2~3편)으로 정리되면 Step 1로 돌아갑니다.

루틴이 정착하면 글 주제가 GSC 노출 데이터로 결정되므로 상상 속 키워드를 쓰지 않게 됩니다. 노출이 발생한 쿼리는 검색 의도가 검증된 키워드이고, 클릭률이 낮다는 것은 제목·메타·내부 링크 중 하나가 비어 있다는 신호입니다. 외부 도구로 자동 트리거하려면 <Link href="/ko/blog/make-automation-guide">Make 자동화 가이드</Link>의 webhook 패턴을 GSC export에 결합하면 됩니다.

## 자주 묻는 질문 (FAQ)

### 글 한 편에 시간이 얼마나 걸리나요?

주제와 확인할 자료의 양에 따라 크게 다릅니다. 자동화가 줄여 주는 것은 파일 변환·이미지·발행·색인 확인 같은 반복 작업이고, 사실 확인과 본인 경험 정리는 여전히 사람의 시간이 듭니다. 오히려 그 부분에 시간을 더 쓰는 것이 이 SOP의 목적입니다.

### Claude 대신 다른 LLM도 가능한가요?

가능합니다. 도구 호출 안정성과 긴 컨텍스트에서 Claude를 선택했지만 핵심은 LLM 자체가 아니라 4단계 구조입니다. GPT·Gemini로도 같은 SOP가 구성됩니다.

### IndexNow가 Google 색인에도 도움이 되나요?

도움이 되지 않습니다. IndexNow는 Bing·Yandex 표준이며 Google은 미채택입니다. Google 색인은 GSC 사이트 등록·sitemap 제출·내부 링크로 해결합니다.

### Obsidian 없이도 워크플로우 구성이 가능한가요?

가능합니다. 핵심은 frontmatter 기반 markdown 노트가 1곳에 모이는 것이고, Notion·VS Code·정적 markdown 폴더도 같은 역할을 합니다.

### Vercel·GitHub 무료 플랜으로 운영할 수 있나요?

개인·비상업 블로그라면 Vercel Hobby와 GitHub Free로 시작할 수 있습니다. 다만 Vercel Hobby는 개인·비상업 용도로 제한되므로 광고·제휴 수익이 있다면 Pro 플랜 약관을 확인하세요. 사용량 한도는 각 서비스의 요금 페이지에서 확인할 수 있습니다.

## 마무리

블로그 워크플로우의 진짜 비용은 글쓰기가 아니라 단계 사이의 빈틈입니다. 빈틈마다 1인 운영자는 결정을 내리고 손을 움직여야 합니다. Claude·Vercel·Obsidian을 한 줄로 엮은 이 SOP는 반복되는 빈틈을 자동화로 메우고, 사람이 판단해야 할 지점만 남깁니다. 도구를 더 늘리는 것보다 단계를 줄이는 것이 1인 운영자의 핵심 전략입니다.
